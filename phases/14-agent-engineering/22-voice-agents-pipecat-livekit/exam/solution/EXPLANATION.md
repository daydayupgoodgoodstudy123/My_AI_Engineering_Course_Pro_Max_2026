# 讲解：VoiceFrame（14/22）

参考实现在 `solution/voiceframe/`。下面按关说明每一处为什么这样写，以及最容易写错的地方。

## Part 1 修打断

课里的 `code/main.py` 有一个 barge-in 演示，但它其实什么都没截断：TTS 在一次 `process` 调用里同步说完整句，transport 发出 cancel 的时候回复早就送完了。这一关的管道把同样的结构做得更像真的，同时留下了三个缺陷。

1. **VAD 把空白当成语音。** `if frame.payload:` 对 `"   "` 也是真。错误出在三层之外：STT 去掉空格得到空转写，LLM 把它作为用户消息交给模型，测试的假模型报 `KeyError: ''`。修法是在 VAD 里用 `str(frame.payload).strip()` 判断。在 LLM 里跳过空转写也能让测试变绿，但根因在 VAD：一个只有空白的块不应该算作用户说话，也不应该触发 STT。
2. **TTS 先合成整句再发第一个词。** 修好以后，每个词合成完就立刻往下游发：

   ```python
   for word in str(frame.payload).split():
       if self.cancelled:
           break
       chunk = self.synthesize(word)
       if self.cancelled:
           break
       self.spoken.append(word)
       super().process(Frame("tts_audio", chunk, turn=frame.turn))
   ```

   两处检查各有用途。第一处在下游播放完一个词、cancel 同步回到这里之后生效；第二处处理 cancel 在 `synthesize` 期间到达的情况：这个词已经合成了，但用户已经开口，不能再播。只保留第一处会挂在 “a word synthesized after the cancel is never played”。
3. **`spoken` 没有按回复清空。** 它记录的是“本次发声已经交给 transport 的词”，cancel 把它带回 LLM，LLM 用它改写最后一条助手消息。只在 `__init__` 里建一次，就会把整通电话说过的词都带上去。清空的位置是每条回复开始的地方，和 `self.cancelled = False` 放在一起。在 cancel 时清空也不对：一条没被打断的回复会留在 `spoken` 里，被下一次 cancel 带走。在回复结束时清空同样不对：用户在机器人刚说完时开口，transport 照样发 cancel，这时它带回的应该是整条回复，清空后带回的是空列表，LLM 会把整条回复改成空串（测试最后一步就是这种情况）。

`spoken.append` 放在 `super().process(...)` 之前，是因为 cancel 可能在这次调用里同步到达（播放回调里用户开口），这时刚播出的词应该算作“听到了”。

## Part 2 通话录制

参考实现的布局：文件以 `MAGIC` 开头，每条记录是一个大端头 `>qBBI`（纳秒时间戳 int64、方向 0/1、kind 长度、负载长度），后面是 kind 的 ASCII 字节和负载原样字节。布局可以不同，测试只通过 `read_recording` 看结果。

- 时间戳用 64 位整数。double 只有 53 位尾数，`1_730_000_000_123_456_789` 这一量级上相邻的两个纳秒值会被存成同一个数。
- 负载按长度读取，不靠分隔符，所以任何字节都可以出现。长度字段要 32 位，测试里有一条 70,000 字节的负载。
- `write` 里 `flush()`：录制的意义在于进程崩溃后还能看，留在缓冲区里的记录在崩溃时会丢。
- 重开时先把文件解析一遍，找到最后一条完整记录的结束位置，如果后面还有字节就 `os.truncate` 掉，再用 `ab` 打开。只在读的时候忽略半条记录是不够的：新记录会接在那半条后面，读的人按半条记录的长度去读，就会错位。用 `r+b` 定位到那个位置直接覆盖写、不截断也不够：新记录比半条记录短时，后面会留下残渣。测试第一次崩溃截在 70,000 字节负载的第 1,000 字节，接着只写一条几十字节的记录，正好暴露这一点；第二次崩溃只留下 3 字节，考的是读的人要先确认头是完整的。
- 参数检查要在 `struct.pack` 之前做，这样 `2**63` 报的是 ValueError，而不是 `struct.error`。下界也要查：`>q` 能装下 `-1`，不查就会写进去。

## Part 3 轮次

`TurnTaker` 维护几样状态：当前轮次已有的片段和它们的置信度、用户是否在说话、最后一次停止说话的时间、机器人正在说哪一轮、已经取消的轮次集合。

- 结束条件有两个。片段到达时，如果拼接后的文本以 `?` 结尾，立刻结束；`tick` 时，如果用户没在说话、距离最后一次停止说话至少 `silence_ms`、而且已经有文本，就结束。
- 置信度取 `min`。一个片段听错，整轮就不可信；取平均会把 0.9、0.4、0.9 平均成 0.73 放过去，只看第一段或最后一段也是 0.9。反过来，把置信度乘起来当成整轮的概率也不对：docstring 要求的是每一段都达到阈值，0.9 和 0.6 两段都达标，乘起来却只有 0.54。
- 低置信度的一轮同样占用轮次号，发出 `Frame("text", REPEAT_PROMPT, turn=n)`，直接给 TTS，不进 LLM。
- 打断只在机器人说话时发生，每个机器人轮次只发一次 cancel，cancel 带那一轮的轮次号。
- `admit` 只认最新一轮，并且排除已取消的轮次。“最新一轮”是最后发出的轮次号，不是 `bot_started` 记下的那一轮：回复的第一帧要先过 `admit` 才能播，机器人这时还没开口。用轮次号而不是一个全局标志，这样取消只影响它自己那一轮；迟到的旧轮次帧也会被丢掉，哪怕那一轮没被取消。

## Part 4 指标

参考实现在读事件的循环里推进窗口：事件时间到了当前窗口的结束位置（`>=`）就先输出当前窗口，再开新窗口，中间跳过的窗口照样输出全 0。流结束时，如果读到过事件，就再输出最后一个窗口。这样每个窗口在关闭的那一刻就被 yield，测试的探针只拉取了 5 个事件就拿到了第一段输出。

推进完窗口才看方向：只有 DOWNSTREAM 帧计数，两个指标族都一样。课里把两个方向分得很清楚，DOWNSTREAM 是数据流，音频进、语音出；UPSTREAM 是反馈和控制，cancel、metrics、barge-in 都走这个方向。练习 1 问的是延迟在哪一段堆积，要看的是数据帧在各段的分布，测验 Q12 的 observer 也只给 downstream 帧记时间。一次打断让 cancel 从 transport 经过 tts、llm、stt、vad 往回走，如果也算进去，打断越多的通话，每一段看起来越忙。UPSTREAM 事件不计数，但它的时间照样推进窗口，stage 名也照样要查。测试把同一通电话去掉打断后的输出拿来比，必须一字不差。

每段输出是两个指标族，各有一行 `# HELP`、一行 `# TYPE`，然后紧跟着按 `stages` 的顺序各一个样本。Prometheus 的文本格式要求一个指标族的所有行连成一组，所以不能先把两行 `# TYPE` 都写在最前面再写样本。`voice_frames_total` 是 counter，所以从通话开始累计；`voice_window_frames` 是 gauge，每个窗口重新数。

标签值用题目里给好的 `_escape` 转义：先反斜杠，再引号，再换行；反过来会把刚加上的反斜杠再转义一次。测试里的 stage 名带着引号、反斜杠和一个换行，检查的是每个标签值都经过了它。`json.dumps` 的结果看起来很像，但它会把非 ASCII 字符写成 `\uXXXX`，Prometheus 的文本格式没有这种转义。

## Part 5 延迟预算

递归函数 `walk(node, using)` 按形状分派：字符串是查表的阶段，list 是串行，dict 按唯一的键分成 `stage`、`first`、`all`、`use`。先判断 `str` 再判断 `list`，类型检查要严格，混合形式（同时有 `stage` 和 `first`）直接报错。带实测区间的阶段也要查阶段名，区间要满足 0 ≤ best ≤ worst。

- 串行：两端各自相加。
- 竞速：最好情况是各分支最好值里的最小值，最坏情况是各分支最坏值里的最小值。最坏时每个分支都慢，但仍然是最快的那个先到。
- 等全部：两端各自取最大值。
- 子管道：`using` 是当前递归路径上的名字。名字已经在路径上才是环；同一个子管道在两个分支里各用一次不是环。用一个全局集合会把第二次使用误判为环。

分档用最坏情况，边界都是闭区间的上端：600 是 premium，1200 是 common，1500 是 slow，超过 1500 才是 broken。课里只给了 450–600、800–1200 和 >1500 三个说法，中间的空档由这道题自己定义。

## 这套题证明了什么，没证明什么

证明了：候选人能在一条双向帧管道里顺着调用链找到上游的根因；理解同步管道里 cancel 是在哪一刻、从哪条调用路径回来的，并据此安排检查点；能设计一个崩溃后还能续写的二进制追加格式；能把“说完了没有”“能不能信”“该不该停”写成一个状态清楚的类；能按真实的 Prometheus 文本格式、按时间窗口在线输出指标，并且分得清数据帧和控制帧；能对嵌套的串行、竞速、等全部结构做递归区间计算。

没证明：真实的音频处理（VAD 模型、STT、TTS 都是假的）；Pipecat 或 LiveKit 的真实 API；并发管道里的队列、背压和跨线程取消；WebRTC 或 SIP 传输；语义轮次检测模型；真实延迟分布的测量。这些需要在真框架和真通话上另外练。
