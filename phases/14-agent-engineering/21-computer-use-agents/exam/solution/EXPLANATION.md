# 参考答案讲解：ComputerUse（14/21）

计时结束后再看。参考实现在同目录的 `computeruse/` 里，`python3 -m pytest --solution --all-parts` 应该显示 5 passed。

## Part 1 修 agent 循环

**现象**：解锁后第一个失败是 trace 对不上。第 2 步本该点中搜索框，trace 里却是 `blocked: no element at (60, 75)`，第 3 步是 `nothing is focused`。这两句都出自 `safety.py`，而分类器本身没有错。

**顺着往上找**：分类器说 (60, 75) 没有元素，那它看到的是哪一屏？`run_agent` 把 `desktop.screen()` 放在循环外面，只取了一次。第 1 步点了链接，`FakeDesktop.navigate` 换成了搜索页；第 2 步点搜索框，`FakeDesktop.click` 又换成一个带焦点的新快照。分类器一直拿着首页在判断。课里说的逐步安全，指的是每个动作都按它执行时的屏幕来判断。这一关想练的是：报错的位置往往不是出 bug 的位置。

**依次修四处**：

1. 把 `screen = desktop.screen()` 移进循环。
2. type 分支补上敏感字段的确认：往卡号、密码框里打字和点敏感按钮一样，要人先同意。点进这个输入框本身不需要确认。
3. 人同意以后，重新取一次当前屏幕，确认那个坐标上最上层的元素还是刚才问过的那个（打字则确认焦点还在那个输入框上），否则记为 aborted，什么也不发给桌面。确认期间界面只是重画、按钮还在原处的，照常执行。
4. `element_at` 改成半开区间：`x <= px < x + w`。

**性能**：线性扫描 76,800 个元素，约 2,000 次查找要 1 到 3 秒。参考实现第一次查找时建一张网格：每 32×32 像素一个桶，元素按绘制顺序放进它覆盖的每一个桶；查找时只看点所在的那个桶，从后往前找第一个覆盖这个点的元素。`Screen` 是快照，建好的网格不会过期。

**护栏**：桶里要倒着找，才能拿到最上层的元素；大元素（对话框）要放进它覆盖的所有桶；边界判断要和 docstring 一致。

## Part 2 截图外部存储

参考实现的布局和 docstring 一致：`objects/<前两位>/<其余 62 位>` 存截图原始字节，`runs/<run_id>.json` 按顺序存步骤记录，每条记录只写截图的 SHA-256 摘要。

- **按字节读写**：截图是二进制，`read_bytes` 和 `write_bytes`。PNG 签名里的 `\r\n` 本来就是用来发现换行转换的，用文本模式读一次，哈希就对不上了。
- **只存一次，不重写**：`put` 先看文件是否存在，存在就读出来校验哈希，内容正确就直接返回，mtime 不变。
- **修复半截文件**：存在但哈希不对，说明是崩溃留下的，先写临时文件，再 `os.replace` 换上去。长度对不说明内容对：测试里那个文件长度正好，100 字节以后全是零，只比长度会把它留下。
- **读的时候校验**：`get` 在文件不在时报 MissingFrame，内容不对时报 CorruptFrame。`load_run` 把它们重新包一层，消息里写明第几步，排查时直接知道是哪一步的截图坏了。
- **往返一致**：步骤记录用 JSON 存，动作参数里的整数坐标、带引号、反斜杠、换行和 emoji 的输入文本都能原样读回；截图逐字节相同。同一个 run_id 再存一次，run 文件整份重写。

## Part 3 跨页面的逐步安全服务

`host_allowed` 用 `urlsplit(url).hostname` 取主机名，它已经去掉了端口和 `user@` 这一段，并且是小写。scheme 只认 http 和 https。`*.` 开头的条目匹配 `.` 加域名这个后缀，所以子域名能过，裸域名和 `badexample-cdn.net` 过不了。

`decide` 按 docstring 的顺序检查，第一个失败的规则就是结果：

1. 当前屏幕的 DOM 里有注入标记，这一屏上的所有动作都拦下。课里的约定是，截图、DOM、工具输出都是不可信输入，不能当作授权。
2. 只认 click、type、navigate。
3. 点击要有目标元素，打字要有焦点。
4. navigate 的 URL 和被点击链接的 href 都要在允许列表里。
5. 输入文本里有注入标记。
6. 人在这一页拒绝过这个元素，直接拦下，不再问。

都通过以后，敏感元素要问人。拒绝时把 (页面 url, eid) 记进 `denials`，这就是课里 Exercise 3 要求的“每次被拒都记下来”，也是第 6 条的依据：只拦这一页上的这一个元素，同一页上的另一个购买按钮照样要问。同意不记，下一次还要问。

`run_session` 每一步都重新取屏幕，给模型看，再拿同一屏去判断；只有 allow 的动作才发给桌面，click、type、navigate 三种都要发。测试里人拒绝了购买；被拦下的导航指向桌面上没有的页面，真发出去会报 LookupError；去 promo 页靠的是一次允许的 navigate。最后核对桌面收到的全部事件。

## Part 4 逐步轨迹

```python
async for action in actions:
    n += 1
    start = clock()
    screen, frame = await desktop.capture()
    digest = store.put(frame)
    verdict = classifier.assess(action, screen)
    ...  # 执行或者不执行，记下 verdict
    yield logfmt(pairs) + "\n"
```

- 每一行在 `yield` 之后才会去取下一个动作，所以测试数到的已取动作数正好等于已输出的行数。
- `start` 在取到动作之后才记，模型思考的 5 秒不算进任何一步。
- logfmt 的值按 docstring 决定要不要加引号：空值、空格、`=`、引号、反斜杠、控制字符都要加引号并转义。URL 的查询串 `q=red+shoes&page=2` 没有空格，也要加引号。远端异常消息里的 `\r\n` 和制表符写成 `\r\n`、`\t`，一行还是一行。参考实现逐个字符查表转义，不会出现先转义引号、再把引号前的反斜杠又转义一次的问题。
- 执行出错时，这一步记 `verdict=error`，再输出 `run=failed failed_step=<n>`，然后 `return`。正常结束输出 `run=ok steps=<n>`。
- 每一步的截图都通过 Part 2 的 store 存下来，被拦下和 held 的步骤也存，行里的 `shot` 是摘要前 12 位，排查第 180 步时直接拿它去找截图。

## Part 5 嵌套界面树的命中测试

`to_screen` 用整数运算：`(2x + 1) * W // (2w)`，就是截图像素覆盖的那段屏幕像素的中点，向下取整，不受浮点误差和银行家舍入影响。

`locate` 递归，每一层带着三样东西往下传：父节点内容区的屏幕原点（已经减去所有祖先的滚动）、当前的裁剪矩形（所有裁剪祖先的交集）、以及点的位置。

- 节点不可见就返回 None，整棵子树都跳过，也不挡住别人。
- 点不在裁剪矩形里，这个节点和它的子树都点不到。每一层都先查这一步，侧边栏和列表两层裁剪就自然取了交集。
- 子节点从后往前试，第一个命中的就是答案，因为后绘制的兄弟和它的整棵子树都在前一个兄弟上面。
- 子节点都没命中，再看点是否在自己的框里。这个顺序让伸出父节点的子节点也能被点到。

最后一组断言把两步串起来：模型在 1280×720 的截图上点 (533, 240)，换算到 1920×1080 的屏幕是 (800, 360)，落在对话框上，而不是对话框下面的文章链接。

## 这套题证明了什么，没证明什么

通过了说明你能在 agent 循环里找出“判断用的屏幕和执行时的屏幕不是同一个”这类错误，能按元素而不是按坐标落实人工确认，能写内容寻址的截图存储并处理崩溃留下的半截文件，能按固定顺序实现逐步安全规则和导航允许列表，能写边执行边输出的 logfmt 轨迹，也能在嵌套界面树里做带裁剪、滚动和缩放的命中测试。它不涉及真实的视觉模型、Xvfb、浏览器或任何厂商的 computer-use API，也不考 OSWorld、WebArena、Online-Mind2Web 上的成绩。课里比较三家模型的部分、重定向链上的导航检查和真实提示注入的识别，需要另外学。
