# 16/08 分关面试题：SOPForge

这是一个写好一半的本地角色工作台：planner 的 `Spec`、executor 的 `Artifact`、结构审阅的 `CriticReport` 和确定性执行的 `VerifierReport` 分开流转。英文题面在 [README.md](README.md)，具体合同在测试、断言消息和 docstring 中。

## 开始

在自己的练习副本打开终端，先读 README 和五个测试的 docstring：

```bash
python3 -m pip install pytest
python3 -m pytest
```

默认五个 skipped 表示关卡按顺序锁住。先解除 Part 1 的 skip，运行 `python3 -m pytest -x`；这一关通过后再解除下一关。

## 规则与时间分配

- 总时长 60 分钟：开场 2 分钟，五关参考分配 12、11、15、10、10 分钟。时间和难度尚未经过真人校准。
- 只修改 `sopforge/` 中的领域实现。测试只解除当前 skip，保留断言和完整正确的 GIVEN 依赖；可以另外写自己的测试。
- 可以查 Python 标准库官方文档。计时期间关闭 `solution/` 和 `INTERVIEWER.md`，边做边解释当前判断。
- 需求不清楚时先问主持人。独练时先写下问题，再只看手册澄清表中的对应答案。
- 每关记录开始、首次通过、运行次数和提示级别；计时结束后的补完另记。

## 五关职责

| 关 | 候选职责 | 完整正确 GIVEN |
|---|---|---|
| 1 修 | 真实函数结构、声明的 callable、全部 case、每次验证只 compile/bind 一次 | `VerificationDesk` gate、真实编译与 once-exec session、查找/逐 case 证据/报告构造 |
| 2 存 | SQLite snapshot 的领域记录布局和 spec/artifact/critic/verifier revision 关联 | tagged codec、建表、事务、物理行顺序、关闭与 bundle link 校验 |
| 3 算 | owner 提问、active answer 匹配、选择性失效、blocked target 恢复 | 显式 presence、有限查找、问题 ID 和带预算的新 revision 构造 |
| 4 流 | 每个真实 verifier case 的身份和自身证据投影 | outcome 分类、JUnit XML 编码、suite counts、async 发布与关闭 |
| 5 构 | 每层 typed role ports、真实 producer/payload kind、声明的 exposes | 完整 `SOPCatalog` 身份解析、payload schema 原语和 revision link 校验 |

P1 的结构 critic 只检查本地明确约定的函数结构，批准不代表行为正确。P1 不实现提问、修订或恢复；这些是 P3 的独立职责。原课脚本的 verifier 已经一次执行代码并跑完所有测试；本题的硬编码函数名、首个成功提前返回和逐 case 重编译是服务练习的预埋回归。完整 `ExecutionSession` 已保证一次 verification 内只 exec 一次；候选仍须消除重复 compile/bind。模块加载异常由正确 GIVEN 转成独立 `load_error`，不是完成的 case，也不是第五个候选缺陷。

P2 按 `(kind, entity, revision)` 保存独立领域记录；完整 snapshot 也保留尚无 artifact 的 planner spec，重开时按 artifact revision 组回各自的 spec 和两种报告。codec 已保留大整数、signed zero、嵌套 tuple/list 和 UTF8；这些是使用给定依赖的集成护栏，不要求重写编解码或事务。

P3 只向缺失 required 字段的声明 owner 提问，不推断答案。匹配 active question、owner 和当前 base revision 后才创建新 revision；只清除依赖这个字段的 step slots，保留无关工作；所有仍未解的 pending step 问题保留原 owner，并按新 revision 重新生成。另一个 target 仍 blocked 时拒绝恢复不同 step；恢复时只运行请求的 blocked target 一次，再真实调用 P1 critic/verifier，不能把 critic 批准改写成 verifier 通过。presence 和最多两次澄清 revision 的预算由完整 helper 提供。

P4 从 `VerifierReport.cases` 生成所有 case，包括成功、值不符和异常。成功不制造 issue，失败保留 expected/got/args，异常保留类型、原消息和这个 case 自己的 args。classname 使用 spec revision，不能替换成独立演进的 artifact revision。分类、空异常消息判别、XML escaping、counts 和传输节奏都由正确 GIVEN 处理；候选仍须选择正确 case、保持顺序和身份。

P5 在每层检查角色输入、输出的真实生产者与 typed payload；即使 kind 和 payload 均正确，错误 producer 仍违反输入合同。只展示本层声明生产且允许 exposes 的输出，exposes 为空时本层输出保留为私有。完整 catalog 提供身份解析、payload kind 识别原语和 revision 关系检查；候选仍负责把真实 payload kind 与本层角色契约逐项比较，并调用关系检查作为次要护栏。短名作用域查找与通用递归所有权不是本题的主要考点。

## 性能与验证边界

P1 fixture 是一个实际含 600 个声明 case 的本地 `TABLE` artifact。预期数据与 fixture 构造在 timer 外；完整 `VerificationDesk.inspect` 和整个 `Bundle` 的相等检查在 timer 内，包含代码、critic/verifier 报告、digest 及全部 case 证据。本机独占完整三慢三快测得慢路径 0.903041 / 0.980894 / 1.125314 秒，参考路径 0.003861 / 0.003669 / 0.004244 秒；限值 0.08 秒，双侧余量为 11.288 / 18.848 倍。六份测量副本仅把 timing assert 换成 elapsed 输出，慢路径另恢复逐 case 的真实 compile/bind；全部功能护栏与另外四关均通过，不表示慢路径通过原限值。原样五测试参考实现已通过；业务 timer 与整个 pytest wall time 分开记录。600 是有限可信代码验证的压力 fixture，不是真实 LLM 数量或任意程序正确性的证明。

当前题包有五个测试、43 条 assert、6 处 `pytest.raises`、五个 skip 锁和 27 项登记错修。当前原样五测试参考实现通过；独立 source-first fresh 的 7 个有效 core 方向初抓 1、漏抓 6，最终均为目标关失败且其他四关通过，全部 matching reference 五关通过。27 项登记错修与默认锁、starter、分层修复、reset 已由规定原 TEMP `--write` 检查器全部通过。完整校准证据保持，数量本身不是通过结果。所有代码输入限于题包声明的本地可信 fixture，`exec` 不是安全沙箱。

## 常用命令

在自己的练习副本运行：

```bash
python3 -m pytest -x
python3 -m pytest -k complete_trusted -x
python3 -m pytest --all-parts -x
python3 -m pytest --solution --all-parts
```

`--all-parts` 和 `--solution` 由本目录 `conftest.py` 提供，真实面试没有。`--solution` 用于计时结束后检查参考实现，不能算作候选实现成绩。

## 结束和重做

1. 到 60 分钟时停下，填写 [REVIEW_TEMPLATE.md](REVIEW_TEMPLATE.md)，把限时结果和之后补完分开。

3. 重做前把自己的 `sopforge/` 和测试另存到一个新目录，再用 `_starter/` 恢复包与五个 skip：

```bash
cp -R _starter/sopforge _starter/tests .
```

恢复后运行 `python3 -m pytest`，应回到五个 skipped。SQLite snapshot、Question/Answer、revision tags、嵌套 SOP 和 JUnit 都是课程概念的本地显式扩展；没有真实模型、网络或原课程脚本执行。
