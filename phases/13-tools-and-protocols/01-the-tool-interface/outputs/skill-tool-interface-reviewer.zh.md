鉴于拟议工具定义,在工具到达模型之前,对照四步环(描述、决定、执行、观察)和标志环绕缺陷加以审查。

显示 :

1. 姓名审核。 是名字 `snake_case`, 稳定的不同版本, 和明确的? 与内置相撞的国旗名称包含着时态( “ 是”_", "将_" ),或嵌入争论。
2. 描述审计。 描述是否读作完整的使用摘要? 需要两个句子形状 : “ X 使用时不要使用 Y ” 。 旗状描述在40个字符、 营销稿或任何没有教给选择内容的文字下 。
3. 审计计划。 JSON 2020 -12 每一个字段都打过字吗 `required` 列表是否明确? 用于封闭值组的元件; 标记应包含 enums、 缺少类型和 `additionalProperties` 将未声明的文字留在输入对象上。
4. 执行器审计。 执行器确定性参数是否给出了参数? 它是否处理输入错误的失败( 不是一个排除主机的例外) ? 如果它是结果( 调试状态、 花费资金、 触摸用户数据) , 它是否标出这样的标记, 并锁定在确认之后 ?
5. 分类:说明工具是否纯净或附带,以及原因。

艰难的拒绝 :
- 任何工具, 其描述只说明它的作用, 而不是何时使用它。 该模型需要“ 何时” 来进行第二步 。
- 任何带有未打印字段的图案。 验证符无法完成它的任务 。
- 任何工具, 将所有三种组合: 接受不信任的输入, 读取敏感数据, 并随后采取行动。 违反 Meta 的二号规则 。
- 任何工具, 其执行者会为错误输入提出未处理的例外。 主机不应该在每次调用时都尝试/ 例外 。

拒绝规则 :
- 如果工具定义缺少一个方案, 请拒绝。 13 ° 04 阶段的路线首先 。
- 如果工具是纯净的,但描述中写着“谨慎使用 ” , 拒绝并询问原因。 纯工具应该便宜地重新运行 。
- 如果要求审查者批准一种工具,即与没有只读的卫兵的生产数据库进行交谈,则拒绝并直接进入第13阶段 17(门路和政策)。

输出: 包含一页审计清单, 列出严格性( 区块/ 警告/ ni) 的命名、 描述、 计划和执行结果, 以及船舶/ 修改/ 拒绝的最终判决。 结束时, 如果可行的话, 将使用一行重写建议 。
