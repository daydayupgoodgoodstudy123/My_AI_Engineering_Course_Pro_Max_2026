## 一、学完本节你应该掌握

### 核心知识点

| # | 知识点 | 一句话要点 |
|---|--------|-----------|
| 1 | 为什么需要多语言模型 | 英语有海量标注，乌尔都语只有几千条，迈蒂利语几乎没有；一个模型同时在多种语言上训练，把高资源语言学到的能力迁移到长尾语言 |
| 2 | 共享词表 | 用在所有目标语言上训练的 SentencePiece / WordPiece 分词器；相关语言中相同的词素映射到相同的子词（如英语和意大利语的 `anti-`） |
| 3 | 共享表示 | 在多语言上做 MLM 预训练的 Transformer，会让不同语言中语义相近的句子产生相近的隐藏状态（mBERT、XLM-R、NLLB 都有此现象） |
| 4 | 零样本跨语言迁移 | 在一种语言（通常英语）上微调，直接在其他语言上推理，无需目标语言标注；语系相近时效果好，相距远时变弱 |
| 5 | 少样本微调 | 加 100–500 条目标语言标注，分类任务可达英语基线的 95–98%（讲义数据），是性价比最高的杠杆；学习率过高会破坏多语言对齐 |
| 6 | 源语言选择 | 语言相似度比语料规模更能预测迁移效果：斯拉夫语目标用德语 / 俄语，印度语目标用印地语，常比英语好；qWALS、LANGRANK 用于量化 / 排序 |
| 7 | 代表模型 | mBERT（104 语，Wikipedia）、XLM-R（100 语，CommonCrawl，base 270M / large 550M）、XLM-V（100 万词表）、mT5（101 语）、NLLB-200（200 语翻译）、BLOOM、Aya-23 |
| 8 | 分词税（tokenization tax） | 生育率税（每词 token 数多数倍）、变体恢复税（拼写 / 变音符 / Unicode 规范化差异变成互不相关的序列）、容量溢出税（留给推理的容量被挤占）；"分词器坏了，靠堆数据救不回来" |
| 9 | 评估 | 按语言分别报告（不要只看聚合）、与单语模型基线对比、非拉丁文字的实体级测试、跨语言一致性 |

## 五、参考答案与解析

### Q1 — 答案：B

讲义定义：在一种语言（通常英语）上微调，推理时在模型支持的任何其他语言上运行，不需要目标语言标签。A 是机器翻译相关的混淆项；C、D 是字面误读。

### Q2 — 答案：B

讲义模型表：mBERT（2018，104 语，Wikipedia，低资源语言弱）；XLM-R（2019，100 语，CommonCrawl，"比 Wikipedia 大得多"，"设定了跨语言基线"，base 270M / large 550M）。XLM-R 是编码器模型，不是解码器（C 错）；更大词表的是 XLM-V（100 万），不是 mBERT（D 错）。

### Q3 — 答案：B

讲义的实践规则："如果目标语言有一个类型学上接近的高资源亲属语言，先用它微调，再与英语微调对比。"印地语与马拉地语同为印度语支、同用天城文、同为 SOV。本节代码也给出 Hindi 排第一（sim=1.00）。D 是本节玩具相似度会导致的误判（见 Q9）。

### Q4 — 答案：A

讲义："低资源语言文本每词被切成的 token 远多于英语，一句印地语可能需要等价英语句子 3–5 倍的 token"，吞掉上下文窗口、训练效率和延迟。

### Q5 — 答案：B

"聚合会掩盖长尾"。100 种语言平均 85%，可能是 90 种语言 90% + 10 种语言 40%。skill 明确："没有分语言评估就拒绝上线。"

### Q6 — 答案：B

讲义 Step 1 的 `classify`：对每个标签用 `hypothesis_template.format(label)` 构造假设句，`tok(text, hypothesis)` 作为句对输入 NLI 模型，取 softmax 后**蕴涵**类的概率（代码中下标为 2）作为该标签分数，再按分数排序。因为模型在多语言 NLI 数据上训练过，同一套 API 对英语、印地语、法语都能用。

### Q7 — 答案：B

讲义："对于 100–500 条目标语言样本，`num_train_epochs=5`、`learning_rate=2e-5` 是安全的默认值。更高的学习率会导致多语言对齐崩溃，你会得到一个只会英语的模型。"大学习率会把预训练得到的共享表示大幅改写。

### Q8 — 答案：B

skill："把分词覆盖率低的文字（阿姆哈拉语、提格利尼亚语、许多非洲语言）标记为需要 byte fallback 的模型。"字节级回退保证任何字符都能被表示，"永远不会 OOV"。C 会丢失信息；A、D 与问题无关。

### Q9 — 参考答案

(1) 日语的特征是 `SOV / Kanji / Japonic`。没有任何候选语言共享文字 `Kanji` 或语系 `Japonic`，唯一能匹配的特征是 **SOV 语序**，而候选中 SOV 的只有 hindi、marathi、bengali、urdu，所以它们都是 1/3 ≈ 0.33。顺序之所以是 hindi → marathi → bengali → urdu：`list.sort` 是**稳定排序**，分数相同时保持原有顺序，即 `LANGUAGE_FEATURES` 字典的插入顺序。

(2) 不可信。"印地语是日语的最佳源语言"只是玩具相似度的产物。缺陷：

- **特征太少太粗**：只有 3 个特征，任何一个匹配就是 0.33 的跳变；真实的 qWALS / lang2vec 使用几十到上百个类型学特征。
- **等权**：语序、文字、语系同等重要，但对子词模型来说，**文字相同**（共享子词）的影响可能远大于语序。
- **精确匹配、没有部分相似**：`SOV` 与 `SVO` 被视为完全不同；`Devanagari` 与 `Bengali` 文字同源也算 0 分。
- **数据过于简化**：日语实际混用汉字与假名，标成 `Kanji` 是简化；而且缺少中文、韩语等真正的候选。
- **只看相似度，不看源语言资源量与预训练覆盖**：LANGRANK 就把语料规模、谱系关系等因素组合起来排序。
- 健壮性：不在表里的语言（如 `korean`）直接抛 `KeyError`。

(3) 加权版本：

```python
FEATURE_WEIGHTS = {"word_order": 1.0, "script": 2.0, "family": 2.0}

def similarity(a, b, weights=FEATURE_WEIGHTS):
    if a not in LANGUAGE_FEATURES or b not in LANGUAGE_FEATURES:
        raise ValueError(f"unknown language: {a if a not in LANGUAGE_FEATURES else b}")
    fa, fb = LANGUAGE_FEATURES[a], LANGUAGE_FEATURES[b]
    total = sum(weights[k] for k in fa)
    matched = sum(weights[k] for k in fa if fa[k] == fb[k])
    return matched / total
```

权重本身也应该由数据决定：在若干"源→目标"实验结果上回归出权重，这正是 LANGRANK 一类方法的思路。

### Q10 — 参考答案

(1) `sim` 只可能是 0、1/3、2/3、1，所以输出只可能是 `0.45、0.60、0.75、0.90`。最大值 `0.45 + 1 × 0.45 = 0.90 < 0.95`，所以 **`min(0.95, ...)` 永远不会起作用**——它只是在参数被改大时防止超过 95% 的保护。

(2) 不能。这是一个**手写的线性示意函数**：基础 45%、按相似度线性加分，两个常数都是拍出来的，没有任何实验数据支撑；打印标签写的也是 `simulated_acc`。它只是为了让"相似度越高、迁移越好"这个**趋势**可视化。

(3) 真实项目里：

- 在候选源语言上**真的做实验**：各用相同的模型和预算微调，在目标语言留出集上测准确率（讲义练习 3：英语源 vs 印地语源，500 条目标语言少样本）；
- 用 LANGRANK 这类学到的排序模型，或 qWALS / lang2vec 的类型学向量相似度来**缩小候选范围**，再挑前几名实测；
- 报告分语言指标与置信区间，而不是单个点估计。

### Q11 — 参考答案

```python
def byte_fertility(text):
    words = text.split()
    if not words:
        return 0.0
    return len(text.encode("utf-8")) / len(words)
```

实测结果：

| 句子 | 词数 | 字符数 | UTF-8 字节数 | 每词字节数 |
|------|------|-------|-------------|-----------|
| `I love this product!` | 4 | 20 | 20 | **5.0** |
| `मुझे यह उत्पाद पसंद है!` | 5 | 23 | 59 | **11.8** |
| `J'adore ce produit !` | 4 | 20 | 20 | **5.0** |

解释：ASCII 字符在 UTF-8 中占 1 字节，而天城文字符占 **3 字节**，且元音符号（如 `ु`、`े`）本身也是独立的码位。对纯字节级分词器（或子词词表覆盖不好、大量回退到字节的情况），同样含义的印地语句子每词要消耗两倍以上的 token——这就是生育率税在字节层面的直观体现。真实子词分词器的生育率要用该分词器实测（`len(tok(text)["input_ids"]) / len(words)`），讲义给出的量级是印地语为英语的 3–5 倍。

关于前几节的正则：

- `re.findall(r"[a-z0-9]+", ...)` 对这句印地语返回 **空列表 `[]`**——所有字符都不是 ASCII，整句话在这些分词器眼里不存在。
- `re.findall(r"\w+", text)` 也**不对**：实测返回 `['म', 'झ', 'यह', 'उत', 'प', 'द', 'पस', 'द', 'ह']`。Python 的 `\w` 不把天城文的元音符号 / 鼻化符号（组合字符）算作单词字符，于是单词在这些符号处被切碎。这正是讲义"变体恢复税"和"非拉丁文字的分词很弱"的缩影——多语言场景必须用为目标文字设计的分词器（SentencePiece 等），并做 Unicode 规范化（如 NFC）。

### Q12 — 参考回答要点

- **机制**：
  1. 共享词表：所有语言共用一个 SentencePiece / WordPiece 词表，相关语言里同一词素对应同一子词，形成"锚点"；
  2. 共享参数与表示：在上百种语言上做 MLM 预训练，模型被迫用同一组参数建模所有语言，语义相近的句子在不同语言中产生相近的隐藏状态（"cat" 靠近 "chat"、"gato"，整句 embedding 也是）；
  3. 因此在英语上学到的"任务头"（例如情感分类的决策边界）作用在共享表示上，换一种语言输入也能工作。
- **边界**：
  - 类型学距离越远（语序、文字、形态）迁移越差；
  - 预训练里数据很少的语言表示质量差（mBERT 在低资源语言上弱）；
  - 分词税：文字覆盖差的语言 token 化碎片化，表示质量下降；
  - 文化 / 领域差异：情感表达、讽刺、实体在不同语言中不同。
- 加分点：讲义"零样本是起点而不是终点"——性能重要时一定要预算目标语言微调；以及"源语言不一定是英语"。

### Q13 — 参考回答要点

- **生育率税**：共享词表主要由英、法、西、中、德等高资源语料训练，长尾语言的词被切成更多 token（印地语可达英语 3–5 倍），消耗上下文、训练算力、推理延迟（API 按 token 计费时还直接意味着更贵）。
- **变体恢复税**：拼写错误、变音符差异、Unicode 规范化不一致（如 `é` 的预组合形式与"e + 组合重音"在字节上不同）、大小写变体，都会变成 embedding 空间里互不相关的序列，模型学不到母语者眼中显而易见的对应关系。
- **容量溢出税**：前两项挤占了上下文位置、层深和 embedding 维度，留给"真正推理"的容量系统性地少于高资源语言。
- **症状**：训练 loss 正常、困惑度看起来合理，但线上输出"微妙地不对"——句中形态崩坏、罕见屈折形式无法恢复。"分词器坏了，靠堆数据救不回来。"
- **训练前发现**：在目标语言留出文本上测量生育率（每词 token 数），与英语对比；检查 UNK / 字节回退比例；检查规范化前后 token 数差异。
- **缓解**：选对目标语言覆盖好的分词器（XLM-V 的 100 万词表是直接修复）；训练前验证生育率；对真正的长尾文字使用 byte fallback（SentencePiece `byte_fallback=True`、GPT-2 式字节级 BPE）；统一做 Unicode 规范化。

### Q14 — 参考回答要点

- **模型**：分类任务用 XLM-R-base（约 270M）作合理默认；若某些语言文字覆盖差，考虑 XLM-V。
- **源语言策略**：不要默认英语。印度语目标先试印地语作源（讲义"对印度语目标，印地语常常胜过英语"）；若没有足够的印地语标注，可以用英语 + 印地语混合；用 qWALS / LANGRANK 缩小候选，再实测（讲义练习 3）。
- **训练**：
  1. 源语言上微调；
  2. 每种语言 300 条做少样本微调（讲义：100–500 条可达英语基线的 95–98%，"性价比最高的杠杆"），`lr=2e-5`、5 个 epoch，学习率不要调大；
  3. 可以把 12 种语言的少样本数据混在一起训练，减少模型数量。
- **数据前检查**：测每种语言的分词生育率，标记高生育率语言。
- **评估**：
  - 每种语言单独的留出集与准确率 / F1（不聚合）；
  - 跨语言一致性：同一条评论的不同语言版本应给出相同预测；
  - 与零样本基线、与（数据足够的语言上的）单语模型基线对比；
  - 实体级测试（非拉丁文字的品牌名、人名）。
- 常见误区：只报 12 种语言的平均准确率；用英语验证集挑超参。

### Q15 — 参考回答要点

1. **拆分到语言**：按语言列出微调前后的准确率，找出下降或很低的语言——聚合指标会掩盖长尾。
2. **查分词**：这些语言的生育率是否异常高、是否大量字节回退 / UNK；线上文本是否有训练集中没有的书写变体（罗马化转写、混合文字、不同 Unicode 规范化形式）。
3. **查数据分布**：少样本数据是否覆盖了线上真实的领域和写法；不同语言的标注质量是否一致。
4. **查训练超参**：学习率是否过高导致多语言对齐被破坏（讲义警告"会变成只会英语的模型"）；是否在某些语言上过拟合。
5. **跨语言一致性**：把投诉样本翻译成英语对照预测结果，定位是理解问题还是标签问题。
6. **对比基线**：与微调前的零样本模型、与单语模型比较，判断是不是微调本身带来了退化。
- 加分点：建立按语言的监控看板和回归测试，每次模型更新都分语言对比。

### Q16 — 参考回答要点

- **LLM 的优势**：零样本 / 少样本能力强，无需训练，覆盖语言多，适合标签体系常变、数据极少的场景（讲义"生成式多语言"栏推荐 Claude、GPT-4、Aya-23、mT5-XXL；LLM 风格的工作可"配合显式的多语言提示"）。
- **XLM-R 仍有价值**：
  - 成本与延迟：270M 的编码器可以在 CPU 上做高吞吐分类，大规模分类时 LLM 的成本高出几个数量级；
  - 分词税同样作用于 LLM：长尾语言每条请求的 token 更多，按 token 计费更贵、延迟更高；
  - 可控、可复现、可本地部署（数据合规）；
  - 有标注数据时，微调后的小模型在单一分类任务上常常不输甚至优于提示式 LLM。
- **常见组合**：用 LLM 生成或扩充目标语言的少样本标注数据，再微调 XLM-R 上线；或者 LLM 处理低流量长尾语言、XLM-R 处理高流量语言。
- 无论用哪个，都要按语言评估。
