## 一、学完本节你应该掌握

### 核心知识点

| # | 知识点 | 一句话要点 |
|---|--------|-----------|
| 1 | 两层缓存 | L2（provider 级）prompt / 前缀缓存复用重复前缀的 attention KV；L1（应用级）语义缓存在 embedding 相似度命中时**完全跳过 LLM** |
| 2 | Anthropic 显式缓存 | 用 `cache_control` 标记可缓存块；TTL 有 5 分钟（写入 1.25 倍基础价）和 1 小时（写入 2 倍）两档；Claude 3.5 Sonnet 读缓存 $0.30/M vs 新鲜输入 $3.00/M |
| 3 | OpenAI 自动缓存 | prompt ≥ 1024 token 时自动生效，无需标记；缓存输入约为新鲜输入的 10%；用 `usage.cached_tokens` 自测命中率 |
| 4 | 前缀必须逐字节一致 | 前缀缓存按"从头开始的相同 token 序列"匹配，前缀里任何一处变化都会让其后的内容全部失效 |
| 5 | 动态内容陷阱 | 系统提示里放精确到分钟的时间、请求 ID、随机打乱的示例 → 每次都是新前缀，只写不读；讲义：ProjectDiscovery 把动态内容移出前缀，命中率从 7% 升到 74% |
| 6 | 并行陷阱 | N 个共享前缀的并行请求在第一次缓存写入完成（约 300 ms）前同时到达 → N 次写入、0 次读取，讲义称账单膨胀 5–10 倍；解法是"先串行一个，再扇出" |
| 7 | 语义缓存命中率 | 讲义（社区数据，非官方基线）：开放式聊天 10–15%，结构化 FAQ / 客服 40–70%，代码问题 20–30%，语音 Agent 50–80% |
| 8 | "95% 准确率"的含义 | 指命中时返回的缓存答案是否合适（匹配正确率），**不是命中率** |
| 9 | 相似度阈值 | 通常从 0.95+ 起步；skill：只有在有回答质量 eval 的前提下才往下调，低于 0.85 有"缓存幻觉"风险 |
| 10 | Batch + 缓存叠加 | Batch API 五折，缓存输入再便宜约 10 倍；讲义称夜间离线任务可降到同步无缓存成本的约 10% |

### 核心技能（能动手做到）

- [ ] 给定 token 数、命中率、写入溢价，算出单次请求和每月的期望成本，并与"不缓存"对比
- [ ] 把一个 prompt 模板拆成"静态可缓存前缀 + 动态后缀"，量化改造前后的成本
- [ ] 计算 5 分钟与 1 小时 TTL 的盈亏平衡点（按每小时请求数）
- [ ] 识别并修复并行陷阱：先串行一个请求写缓存，或提前预热
- [ ] 读懂 `simulate()` 的 L1 / L2 逻辑，并指出它在并行波次、TTL、阈值上的建模简化
- [ ] 为语义缓存选择阈值并设计回答质量评估与失效策略

## 五、参考答案与解析

### Q1 — 答案：B

讲义："L2 (provider-level) prompt/prefix caching reuses attention KV for repeated prefixes ... L1 (app-level) semantic caching skips the LLM entirely on embedding similarity hits."

- A 错：L1 在应用层。
- C 错：L2 命中只省掉前缀的 prefill（以及前缀部分的输入费），仍然要生成输出、仍然收输出费。
- D 错：逐字节一致是 L2 前缀缓存的要求；L1 正是为了"意思相近但字面不同"的请求而设计，靠相似度阈值匹配。

### Q2 — 答案：D

`CACHE_WRITE_5MIN = 1.25 × 3.00 = 3.75`，`CACHE_WRITE_1HR = 2.00 × 3.00 = 6.00`，`CACHED_INPUT = 0.30`。

- A 忽略了写入溢价。
- B 把 1 小时写成 1.5 倍。
- C 把倍数当成了价格。

### Q3 — 答案：A

前缀缓存存的是"从第一个 token 开始的某段前缀"的 KV。注意力是因果的，后面 token 的 KV 依赖前面所有 token，所以只要开头变了，后面再相同也不能复用。这就是讲义的 "dynamic content anti-pattern"，解法是把固定内容放前面、动态内容放在缓存边界之后。

- B 错：3,000 token 远超 OpenAI 的 1024 门槛。
- C 错：provider 并不识别"时间"。
- D 错：即使 TTL 无限长，前缀每次都不同也不会命中。

### Q4 — 答案：C

讲义："the first cache-write completes around 300 ms after the provider sees the prompt. Requests 2-10 arrive in the same millisecond window and each sees cache miss. You pay 10 write premiums, 0 read discounts." 解法："make request 1 alone, then fire 2-10 once 1's cache has populated. Adds 300 ms to the first tool call; saves 5-10x the bill."

- A 是"理想情况"，现实中写入有延迟。
- B 错。
- D 错：TTL 只影响缓存能活多久，不能让"还没写好"的缓存提前可用。

### Q5 — 答案：D

讲义："Vendor '95% accuracy' refers to match correctness, not hit rate." 生产命中率从开放式聊天的约 10% 到结构化 FAQ 的约 70% 不等。

- A 是最常见的误读。
- B 是阈值，与准确率是两回事（阈值 0.95 只说明相似度要求高）。
- C 与缓存准确率无关。

### Q6 — 答案：A

写入：`8,000 / 1e6 × 3.75 = $0.030`；读取：`8,000 / 1e6 × 0.30 = $0.0024`（实际计算）。读取比写入便宜 12.5 倍，比新鲜输入（$0.024）便宜 10 倍。

- B 把写入算成了新鲜价、读取算错。
- C 用的是 1 小时 TTL 的写入价（6.00 × 0.008 = 0.048）。
- D 的 $0.024 是新鲜输入价，不是读取价。

### Q7 — 答案：C

期望 = `500 × (0.6 × 1 + 0.4 × 5) = 1,300`。实际运行生成了 **1,304** 个请求，其中 1,005 个属于并行波次（201 个波次）。标题 "500 requests" 指的是循环次数，不是请求数，属于代码里的小误导。

- A 是循环次数。
- B 是 `500 × 1.4`，误以为波次只多 1 个请求。
- D 是把每次循环都当作波次。

### Q8 — 答案：B

讲义："automatic caching for prompts ≥1024 tokens ... No explicit flag ... Neither docs nor release notes publish an official hit-rate baseline ... Monitor `usage.cached_tokens` to measure your own."

- A 是 Anthropic 的做法。
- C 错：缓存输入约为新鲜输入的 10%。
- D 错：缓存与 Batch 是两种独立机制，可以叠加。

### Q9 — 参考答案

实际检查（用 `make_workload()` 默认参数）得到的事实：

1. **同一波次的请求并不共享前缀**：每个请求都独立 `rng.choice(prefixes)`。201 个波次里，5 个请求前缀全相同的波次是 **0 个**（多数波次有 4–5 种不同前缀）。而讲义的并行陷阱恰恰是"10 个请求共享同一个系统提示"。
2. **并行请求永远不写入缓存**：惩罚分支只计费、不 `l2_cache.add`。只有非并行请求才能把前缀放进缓存；一旦某个前缀被单独请求写入，之后的并行请求照样读取。由于只有 12 个前缀，很快就全部被写入，惩罚只体现在最开始的 77 − 12 = 65 次额外写入上。
3. **没有"写入延迟窗口"**：现实中只有"第一个写入完成前到达"的请求才会 miss；代码的惩罚是"并行请求 miss 时永远不缓存"，与真实机制不同。
4. **TTL 没有实现**：`arrived_at` 从未被使用，缓存永不过期。整个工作负载只跨越约 519 秒（约 8.7 分钟），同一前缀的最大间隔约 57 秒，5 分钟 TTL 已足够。`ttl` 只影响写入价，所以在本模拟中 1 小时 TTL **只会更贵**（单独把 TTL 改成 1 小时、不开 L1：$5.96 vs $5.85）。最后两行同时改了 TTL 和 L1，省下的钱完全来自 L1。
5. **`l1_threshold` 没被使用**：L1 命中是一个与内容无关的固定概率 `l1_hit_prob`，阈值只是摆设；L1 命中也不计 embedding 查询成本。
6. **整个 prompt 都被当作可缓存前缀**：没有"动态后缀"的部分，也就模拟不了讲义的动态内容陷阱；而且缓存只按 `prefix_hash` 判断，同一个前缀的请求长度却在 2,000 / 4,000 / 8,000 之间随机变化。
7. 输出固定 200 token，全部 1,304 个请求的输出成本是 $3.91，占缓存后总成本的大头，进一步稀释了输入侧的差异。

结论：惩罚被稀释，是因为模型里"共享前缀的并行波次"几乎不存在，而且缓存一旦被非并行请求写好就不再受并行影响。输入侧成本之比是 `2.93 / 1.94 ≈ 1.51` 倍，含输出后约 1.17 倍。

### Q10 — 参考答案

（以下数值均用 Python 计算。）

1. 并行全部写入：`10 × 4,000 / 1e6 × 3.75 = $0.150`。
2. 先串行 1 个再并发 9 个：`4,000 / 1e6 × 3.75 + 9 × 4,000 / 1e6 × 0.30 = 0.015 + 0.0108 = $0.0258`。相差 `0.150 / 0.0258 ≈ 5.8` 倍——正好落在讲义的"5–10 倍"区间。
3. 不开缓存：`10 × 4,000 / 1e6 × 3.00 = $0.120`。"并行 + 开缓存"是 $0.150，**比不开缓存还贵 25%**——每次都付写入溢价而从不读取。
4. 加上 10 × 200 输出 token（$0.030）：`(0.150 + 0.030) / (0.0258 + 0.030) ≈ 3.2` 倍。说明"5–10 倍"指的是输入侧（前缀）成本；输出占比越高，倍数越小。

### Q11 — 参考答案

1. 每次间隔都超过 5 分钟，5 分钟 TTL 下每次都要重新写入：`C_5min = 1.25k`。1 小时 TTL 下第一次写入、其余读取：`C_1h = 2 + 0.1(k − 1)`。
2. 令 `1.25k > 2 + 0.1(k − 1)`，得 `1.15k > 1.9`，`k > 1.65`。所以**每小时只要有 2 次（间隔 > 5 分钟）的复用**，1 小时 TTL 就更划算：k = 2 时 2.5 vs 2.1，k = 5 时 6.25 vs 2.4（实际计算）。
3. 如果请求间隔总小于 5 分钟，5 分钟 TTL 的缓存会一直保持活跃（讲义只说明了两档写入价；通常命中会刷新 TTL，具体以官方文档为准），只需写入一次（1.25），之后都是读取，比 1 小时 TTL 的一次写入（2）更便宜，应选 5 分钟。skill 的规则正是："1-hour wins when the prefix is reused within the hour consistently"。

### Q12 — 参考答案

1. 改造前：`3,050 × 3.75 / 1e6 + 500 × 3.00 / 1e6 = 0.0114375 + 0.0015 ≈ $0.01294`。
2. 不开缓存：`3,550 × 3.00 / 1e6 = $0.01065`。
3. 改造后：`3,000 × 0.30 / 1e6 + 550 × 3.00 / 1e6 = 0.0009 + 0.00165 = $0.00255`。
4. 结论：
   - 动态内容留在前缀里时，开缓存比不开**还贵约 21%**（只付写入溢价、没有读取）。这就是讲义 The Problem 中"账单没降"的原因，也是 skill 拒绝签字的情形之一。
   - 改造后单次输入成本约为改造前的 1/5（`0.01294 / 0.00255 ≈ 5.1`），比不开缓存便宜约 76%。
   - 命中率从约 0% 变为接近 100%（同一前缀在 TTL 内只需写一次）；ProjectDiscovery 的实际数据是 7% → 74%。

### Q13 — 参考回答要点

- **缓存的是什么**：前缀 token 在每一层的 K、V（attention KV cache）。命中时 provider 直接加载这些 KV，省掉前缀的 prefill 计算，只对新增部分做 prefill。
- **为什么要逐字节一致**：因果注意力里第 i 个 token 的 KV 依赖前面全部 token，前缀任何一处不同，后面的 KV 都不同；因此缓存按前缀（通常按块）哈希匹配。
- **为什么读便宜**：省掉了前缀的 prefill 算力，TTFT 也随之降低（讲义：Anthropic 称长 prompt 最多可降 90% 成本、85% 延迟）。
- **为什么写更贵**：要额外把 KV 存储下来并在 TTL 内占用显存或更低层级的存储；TTL 越长占用越久，所以 1 小时写入（2 倍）比 5 分钟（1.25 倍）贵。
- 加分点：自托管时同样的机制叫 prefix caching / RadixAttention（[阶段 17 · 06](../../06-sglang-radixattention/docs/zh.md)）；OpenAI 自动缓存、Anthropic 显式标记、Gemini 显式 context caching 是三种产品形态。

### Q14 — 参考回答要点

- 只看前缀 P 的 L2 期望单次成本（价格单位 $/token，写入倍数 w）：
  `E[C] = h · P · p_read + (1 − h) · P · w · p_in + O · p_out`
  不开缓存：`P · p_in + O · p_out`。
- **开缓存反而更贵的条件**：`h · p_read + (1 − h) · w · p_in > p_in`。代入 `p_read = 0.1 p_in`、`w = 1.25`：`0.1h + 1.25(1 − h) > 1` → `h < 0.217`。即命中率低于约 22% 时，5 分钟 TTL 的缓存会比不缓存还贵；1 小时 TTL（w = 2）时门槛是 `h < 0.526`。
- **叠加 L1**（命中率 h1，命中时只付 embedding 查询成本 e）：
  `E[C] = h1 · e + (1 − h1) · E[C_L2]`。L1 命中同时省掉输出费，所以输出占比高的场景 L1 的价值更大。
- **其它要计入的成本**：L1 错误命中的业务代价（错误答案）、向量库的存储与查询、缓存失效带来的工程复杂度。
- 加分点：能现场算出 22% 这个门槛，并指出 Q12 的例子正是 h ≈ 0 的情况。

### Q15 — 参考回答要点

- **排查清单**：
  1. 前缀里有没有动态内容：时间、日期、请求 ID、用户名、随机示例顺序、检索结果放在系统提示前面；
  2. 序列化是否稳定：工具定义 / JSON 的键顺序、空白、版本号是否每次一致；
  3. 是否有并行扇出（Agent 工具调用、批量子查询）；
  4. prompt 是否达到缓存最小长度（OpenAI ≥ 1024 token）；
  5. Anthropic 是否正确放置了 `cache_control` 断点；
  6. TTL 是否与请求间隔匹配。
- **改造**：静态规则 / 示例 / 工具定义放最前并标记缓存；RAG 检索内容和用户问题放在缓存边界之后；时间精度降到"天"或移到末尾；并行改为"先串行一个再扇出"或预热。
- **监控**：skill 要求的"过去滚动一小时 L2 命中率，下降超过 20% 就告警"；按模板版本统计 `cached_tokens / prompt_tokens`；每次模板变更后重新审计。
- 常见误区：以为"开了缓存开关"就完事；以为命中率低是 TTL 太短。

### Q16 — 参考回答要点

- **阈值**：从 0.95 起步（讲义与 skill）；用带标注的离线集画"命中率—错误命中率"曲线，按业务可承受的错误率选点；skill 规定没有回答质量 eval 不得降到 0.85 以下。讲义练习 4 的情形（0.85 命中 50% 但出现错误答案）应选更高阈值，除非错误答案的代价可量化且低于节省的成本。
- **防错与越权**：
  - 缓存键要包含租户 ID、模型版本、系统提示版本、语言等上下文，绝不能把 A 租户的个性化答案返回给 B；
  - 只缓存"与用户无关"的通用回答（FAQ 类），涉及账户、订单、个人数据的请求直接绕过 L1；
  - 对命中的答案做抽样复核。
- **失效**：知识库或政策更新时按标签 / 版本批量失效；设置 TTL；人工标记的错误答案立即删除。
- **是否值得**：用讲义的命中率区间估算（客服 40–70%），算 `h1 × (单次 LLM 成本) − 向量库成本 − 错误命中代价`；开放式聊天（10–15%）往往不值得。
- 加分点：L1 与 L2 互补——L1 命中直接跳过 LLM，未命中的请求仍可享受 L2 前缀缓存。

### Q17 — 参考回答要点

- **问题**：10 个子查询同时发出，都在第一次写入完成前到达，全部写入、没有读取。
- **不加延迟的做法**：
  1. **提前预热**：前缀是静态的，可以在会话开始、用户还在输入时，先发一个只含共享前缀、`max_tokens` 很小的请求把缓存写好；等真正的问题来了，10 个子查询都能命中。
  2. **保持热度**：对高频前缀，在 TTL 内定期用最小请求续期（或使用 1 小时 TTL），使缓存一直处于可用状态。
  3. **重叠执行**：先发 1 个最关键的子查询，在等待它返回的同时（约 300 ms 后缓存已写好）再发其余 9 个——第一个子查询本来就在关键路径上，其它子查询的延迟被它掩盖。
  4. **合并请求**：如果子查询之间相互独立且较短，可以合并成一次请求、结构化输出多个结果。
- **衡量**：对比改造前后的 `cached_tokens` 比例与端到端 P50/P99 延迟。
- 常见误区：直接串行全部 10 个（延迟乘 10）；以为换 1 小时 TTL 就能解决并行问题。
